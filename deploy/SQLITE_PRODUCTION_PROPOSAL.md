# L-01 替代方案：单机 SQLite 持久部署

来源：用户询问“只用 SQLite 是否可以实现”。结论：**可以；无需为了数据库名称而引入云数据库。当前尚缺可用运行位置和持久盘验证。** 此文件是提交 lead 的具体设计调整建议，不修改 `docs/lead/` 的冻结基线，不代表部署已经通过。

## 建议配置

- 一台持续运行的服务器/VM；单个产品服务实例。可在本机浏览器验收，但用户电脑休眠/关机就不能持续监控。
- SQLite 文件置于应用发布目录以外的持久本地块磁盘，例如 `/var/lib/watchlist/monitor.sqlite`；重新发布代码不得删除此目录。
- 事务、唯一约束、租约、owner 校验继续使用现有实现。当前规模是演示账户、最多 10 个任务，适合单机数据库。
- 独立系统定时器每分钟调用产品鉴权 tick，服务进程故障由进程管理器重启；不以浏览器计时器代替。
- 使用 SQLite backup API 做一致性备份，备份保存到独立持久位置并测试恢复。不要在运行时仅复制 `.sqlite` 文件而遗漏 WAL 状态。
- 公网 TLS/访问保护由反向代理负责。应用只监听 loopback；公网 URL 与目标平台仍待指定。
- 不把 WAL 文件放在 NFS 等共享网络目录；不做跨机器直接共享 SQLite 文件。不承诺自动水平扩容或高可用。

## 当前运行时的具体处理

实测 Python 的 SQLite 为 3.51.2。SQLite 官方说明 3.51.3 修复 WAL-reset 并发问题；3.50.7 / 3.44.6 也有回移修复。当前实现对未修复版本使用 rollback DELETE journal，并显式 FULL synchronous；版本足够新时才启用 WAL。保留事务锁和超时，测试针对实际 journal 模式执行。不需要为此迁移成云数据库。

来源：
- https://www.sqlite.org/whentouse.html （SQLite 支持中低流量网站与应用服务）
- https://www.sqlite.org/wal.html （同机约束、WAL 文件持久性与 WAL-reset 修复版本）

## L-01 关闭证据仍不可省略

1. 明确服务器、目录、持久盘类型及生命周期；排除容器临时层。
2. 目标环境创建 Task/RuleVersion/Run/Evidence/Notification 后，重启服务、重新发布代码，逐项读回相同 ID 和记录。
3. 并发与重复 tick 的通知数不增长；在途编辑/暂停不得发布旧提醒。
4. 备份恢复到独立文件，经 `integrity_check` 后读回上述记录。
5. 无网页访问时独立调度至少三次，并与产品数据库记录对应。

如果继续限定秒悟且无法提供已验证持久卷，SQLite 本身无法补救临时磁盘问题；需要换运行位置，或使用外部持久数据库。暂时保留 production 启动保护，待目标环境验证和 lead 基线调整后移除。
